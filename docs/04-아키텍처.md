## 2. 스택 선정 근거

| 계층 | 선정 | 왜 |
|---|---|---|
| Collector | **Python** — httpx, tenacity, polars | 공공 API REST/XML. 파이썬이 압도적. SQLAlchemy |
| 스케줄 | **Dagster** | Airflow 대비 설정·운영이 가볍고, dbt 같은 asset 중심 모델. **소규모 팀에 적합** |
| Core/API | **FastAPI** + Pydantic | 룰 엔진이 Pydantic 스키마로 정의되면 **판정 로직이 곧 스키마 검증**이 됨 |
| Store | **PostgreSQL + PostGIS** | 좌표 기반 생활권/통근 계산. Alternative로 PostGIS이 사실 유일 |
| Front | **Next.js** + MapLibre GL | 지도 필수. Google Maps는 비쌈. MapLibre + OSM raster/vector |
| 실시간 | **SSE** | 알림은 양방향성이 약함. WebSocket은 과함. SSE가 충분 |
| 알림 | **AlimTalk / 카카오 Biz 메시지** | SMS보다 저렴, 링크 지원. 도입 후 확장 |

### 의도적으로 쓰지 않는 것
- **LLM을 판정에 쓰지 않는다** — 비용·재현성·컴플라이언스 3중 이유로 금지 (03-법적리스크 4절)
- **Graph DB** — 관계가 복잡하지 않음. Postgres로 충분
- **마이크로서비스** — 규모 대비 오버헤드. 모놀리트로 시작

## 3. 데이터 파이프라인

### 3.1 수집 주기

| 대상 | 주기 | 비고 |
|---|---|---|
| 실거래가 (월 단위 데이터) | 매일 1회 | LAWD_CD(법정동 5자리) × DEAL_YMD(계약월) 로 순회 |
| 공동주택 기본정보 | 주 1회 | 단지 마스터. 변경 드묾 |
| REB 청약/분양/경쟁률 | 매일 2회 (09/18시) | 공고 접수는 업무시간 |
| LH 공고·공급 | 매일 2회 | |
| HUG (분양가·지수·든든전세) | 매일 1회 | |
| SGIS (인구·사업체) | 월 1회 | census 기반이라 갱신 드묾 |
| ECOS (금리) | 매일 1회 (08시) | |
| 법령·시행일 | **매주 1회 +idtă 유효 개정 시 자동** | 시행일 기준 90일 예고 알림 |

### 3.2 실거래가 수집 패턴

```
for DEAL_YMD in [현재월 - 3개월 ~ 현재월]:   # 지연분포 감안해 3개월 슬라이딩
    for LAWD_CD in 자치단체 목록 (약 250개):
        fetch(LAWD_CD, DEAL_YMD)  → upsert
```

- **리트라이**: tenacity, 429/5xx만 지수 백오프
- **레이트리밋**: 일일 1,000~10,000 (개발계정). 운영계정 상향 신청 전제로 설계
- **멱등성**: `(LAWD_CD, DEAL_YMD, dedup_key)` unique. 재수집 안전
- **지연 계측**: `계약일 → 수집일` 간격 분포를 매번 기록. **이게 곧 서비스의 신뢰도 지표**

### 3.3 단지 정규화 (가장 중요)

실거래가에는 `아파트명` 문자열만 있다. `"e편한세상"` 하나가 전국에 15개 있다.
정규화 실패 = 점수 계산 오염.

```
기준: 국토교통부 공동주택 기본정보 (AptBasisInfoServiceV4) → 단지코드
방법: (지역코드 + 정규화 아파트명 + 준공연도) 로 단지코드 매핑
     실패 건은 별도 큐에 남기고 수동 확인 (자동 추측 금지)
```

> 이 테이블 없으면 Phase 1의 "실거래 대비 괴리"가 무의미해진다.
> **우선순위 P0.**

## 4. 판정 엔진 — 결정론 보장

### 4.1 룰 스토어

```yaml
# rules/chat_apt_apt_general_2026.yaml
id: chat_apt_general
region_scope: metro          # metro | non_metro
housing_type: APT
supply_type: 일반공급
effective_from: 2024-03-05
effective_to: null
legal_basis:
  - "주택공급에 관한 규칙 제9조"
  - "국민주택기금법 시행령 ..."
checks:
  - key: homeowner
    required: true
    source: 사용자_재무프로필
  - key: subscription_period
    required: true
    unit: 개월
  - key: income
    threshold: {1인: 8000, 가족: 12000}   # 단위: 만원/년, 세대구성원 기준
  - key: net_assets
    threshold: {1인: 36000, 가족: 48000}
effect:
  eligible_when_all: [homeowner, subscription_period, income, net_assets]
on_unknown: "manual_review"     # ← 'false' 아님. 판정 불가를 '실패'로 처리하지 않는다
```

### 4.2 감사 로그

**모든 판정은 다음을 통째로 기록한다.**

```json
{
  "decision_id": "...",
  "ts": "2026-10-07T12:00:00Z",
  "rule_set_id": "chat_apt_general",
  "rule_set_version": "2026-03-05",
  "profile_snapshot": { "...": "암호화된 참조" },
  "input": { "LAWD_CD": "11680", "순자산": 32000, "소득": 7500 },
  "result": { "eligible": true, "reasons": [], "failed": [] },
  "legal_basis_links": ["..."],
  "disclaimer_hash": "..."
}
```

> 판정 결과가 나중에 법이 바뀌면 **왜 그때 그렇게 나왔는지** 재현되어야 한다.
> 이것이 신뢰의 근간이다. Rule Set은 Git에 versioning (코드 리포와 동일).

## 5. 알림 파이프라인

```
Collector 완료
  → EventBus.publish({type, entity, payload})
  → EventMatcher: 구독 중인 사용자 중 조건 충족자 필터
  → Dedup (사용자+이벤트유형, TTL)
  → Priority 분류 (긴급/높음/보통)
  → NotificationQueue
  → [긴급] 즉시 발송
  → [일반] 09:00 다이제스트 배치
  → 발송 결과 피드백 → 선호도 학습 (알림 무응답 → 쿨다운)
```

### 매칭 쿼리 (PostGIS 예시)

```sql
-- 통근 45분 내 + 예산 내 + 조건 충족 매물 신호
SELECT s.id, s.source_url,
       ST_Distance(s.geom, p.workplace)        AS dist_work,
       ST_DWithin(s.geom, p.workplace, 45000)  AS in_commute
FROM signal s
JOIN profile p ON p.user_id = :user
WHERE s.price BETWEEN p.budget_min AND p.budget_max
  AND ST_DWithin(s.geom, p.workplace, 45000)
  AND s.score >= :threshold;
```

> 통근시간은 거리로 근사하지 않는다. **지도 API isochrone**으로 폴리곤을 구해
> `ST_Within` 판정한다. 도심은 3km와 8km의 통근시간 차이가 크다.

## 7. 개발 순서 (의존성 순)

```
[1] 단지 정규화 테이블        ← 다른 모든 것의 전제
      ↓
[2] Collector + Store
      ↓                    ↘
[3] Rule Store + 판정 엔진   [4] 비용 계산기
      ↓                    ↗
[5] EventBus + 알림
      ↓
[6] API + Web
```

[3]과 [4]가 MVP의 심장. [1]을 못 만들면 [2]부터 의미가 없다.

## 8. 2026-11 조사 반영 — 정책 신뢰 레이어

정책 이벤트를 다루는 순간 이 레이어가 필수다. "무엇이 바뀌었는지"보다
"이것이 진짜인지"를 판정하는 것이 제품 가치의 핵심이 된다 [리포트 58].

```
[PolicyTrust Collector] → [CrossCheck] → [PolicyRule] → [EventBus]
        공식 소스만             2중 이상 일치     시행일·대상 매핑      verified만
```

### 8.1 수집 (공식 소스만)

| 소스 | 방식 | 주기 | 비고 |
|---|---|---|---|
| 국토교통부 X @Korea_land | 공식 계정 모니터링 | 실시간 | 계정 인증·라벨 확인 필수 |
| 국토교통부 Threads | 공식 계정 모니터링 | 실시간 | 2026-06-25 개설, 개설 당일 1만 2천 팔로워 |
| 정책브리핑(korea.kr) | RSS·HTML 파싱 | 일 1회 | 브리핑 원문 |
| 법제처 법령 API | 현행 조문·개정일·시행일 | 일 1회 | 룰의 `effective_date` 근거 |
| 국세청 | 증감·고시 | 주 1회 | 세제 일정 |

보도자료만으로는 지라시와 진짜를 구분할 수 없다. 공식 SNS는 **검증용** 소스로,
보도자료는 **내용 확인용** 소스로 역할을 나눈다.

### 8.2 교차 검증 규칙

- 단일 출처 기사는 발송하지 않는다. 공식 소스 2개 이상이 일치할 때만 확정한다.
- "취득세 35% 감면" 같은 수치에는 반드시 **시행일 + 적용 대상 범위**를 함께 붙인다.
- 소급 적용 여부를 `effective_date` 규칙으로 판정한다.
- 검증 실패 시 상태는 `PENDING_VERIFICATION`이다. 대시보드에는 보이지만 알림으로는 나가지 않는다.

### 8.3 저장 스키마

```yaml
policy_event:
  id: "policy_2026_11_acquisition_tax"
  source:
    - channel: "x"
      account: "@Korea_land"
      url: "https://x.com/..."
      captured_at: "2026-11-13T08:12:00+09:00"
    - channel: "law"
      service: "law.go.kr"
      article: "지방세법 시행령 ..."
      effective_date: "2026-12-15"
  claim: "취득세 감면율 조정"
  affected: ["수도권_취득세", "영끌_약제"]   # 사용자 조건으로 매핑되는 태그
  confidence: "verified"   # verified | pending_verification | rejected
  verified_at: "2026-11-13T09:03:00+09:00"
```

`confidence`가 `verified`가 아닌 항목은 EventBus에 publish하지 않는다.
거부(`rejected`)된 항목은 감사 로그에 남겨 같은 지라시 재발 시 즉시 차단한다.

### 8.4 이벤트 타입 추가

기존 6종에 `POLICY_TRUST`를 추가한다. 다른 정책 이벤트와 달리 "발생"이 아니라
"신뢰도 확정"을 의미한다.

| 이벤트 | 의미 | 발송 조건 |
|---|---|---|
| `POLICY` | 정책·법령 변경 감지 | 변경 사실 확인 |
| `POLICY_TRUST` | 지라시 검증 결과 확정 | 공식 소스 2중 교차 확인 |

### 8.5 GEO 대응

AI 검색 노출을 고려한 구조화 근거가 필요하다. 판정 결과는 사람이 읽는 화면과
기계가 읽는 표를 함께 제공한다.

| 화면 요소 | 기계가 읽는 형태 |
|---|---|
| 판정 결과 | 결과값 + 단위 + 기준일 + 조건 태그 |
| 근거 | 조문 번호 + 시행일 + 원문 URL |
| 지표 | 지표 ID + 출처 + 산식 + 기준값 |
| 계산 | 입력값·중간값·결과값의 명시적 표기 |

이렇게 하면 판정 엔진 자체가 유통 채널이 된다. 외부 측정 서비스가 앱을 추천하는
순위(호갱노노 100 / 네이버 91 / 직방 85.8)에서 뒤처지지 않으려면 정확성과 근거 링크가
곧 노출이 된다 [리포트 21].
